### 2026-11-12 — T005 merged: /start, repo + SHA cache, Inngest job, status page
**Decision**: `/start?url=` and `POST /api/start` resolve the default-branch HEAD with one GitHub call (`GET /repos/o/n/commits?per_page=1`, app token `GITHUB_APP_TOKEN`), then return a cache hit (`/ladders/:id`, built by T010) or create one open job per repo + SHA (partial unique index) and send an Inngest event; `/jobs/:jobId` polls every 2 s. Added beyond the guide: table `generation_job_waiters`, column `reset_at`, error codes `repo-empty` 422, `github-unavailable` 502, `queue-unavailable` 503, `too-many-starts` 429 (limit `START_MAX_NEW_JOBS_PER_HOUR`, default 20 new jobs per learner per hour, counted under an advisory lock). Production refuses `INNGEST_DEV` and requires `INNGEST_SIGNING_KEY`, `INNGEST_EVENT_KEY`, `INNGEST_SERVE_ORIGIN`. The job function reads repo and SHA from its `generation_jobs` row, not from the event. SC 7 e2e runs the Inngest function in-process (`@inngest/test`); `inngest-cli` was not installed because the auto-mode classifier blocked `bun pm trust`.
**Why**: T005 acceptance criteria; auto verify pass 2026-11-12 (commit fdd8580); code-review 0 P0/P1; security P1 (no per-learner limit) fixed, re-review GO.
**Known gaps (for T018 or before public launch)**: the limit runs after the GitHub call, so requests over the limit and cache hits still spend the shared token (needs a per-request limiter); a job can stay `queued` forever if the process dies between saving it and sending its event; `queue-unavailable` jobs count against the limit; `INNGEST_SERVE_ORIGIN` accepts a value whose origin is `"null"` and the production checks run only when `NODE_ENV` is exactly `production`; a huge `x-ratelimit-reset` can still throw; the `fetched` update has no status guard; the real Inngest dev-server run and the real `GITHUB_APP_TOKEN` run are the owner's manual checks and were not done; the `wip(T005)` commit stays in history.

### 2026-11-12 — T011 merged: daily 5-minute review, FSRS (ts-fsrs 5.4.2), append-only review log
**Decision**: `/review` page + `GET /api/review/queue` + `POST /api/review/rate` (`rateCard`; the guide first called it `submitReviewRating`). Migration `0005_review` (0003 stays reserved for T006's unmerged `0003_core_files`; the runner applies pending migrations in name order, so it still applies later): `review_cards` (T008 will write the rows; T011 only reads), `card_states` (per learner, created lazily on the first rating, no row = New and due now), `review_log` (append-only trigger, unique key per learner, no cascade: a ladder, card or learner with history cannot be deleted row by row, data deletion is T018's). Unlocked level = `levelLockState` not `locked` via the T010 `passedLevels` seam. Queue: at most 50 cards, due ascending, New cards after due ones and capped at 10 per queue response (not per day: user kept it, a learner who rates 10 New cards gets 10 more on the next load; the 5-minute session is the only brake). Migration-safety: GO, the dry-run-on-production-data box accepted as N/A by the user (no production database; reopen for the first migration after T018 deploys). Client: one card at a time, Space shows the answer, keys 1-4 rate, 5:00 timer from the first card (client clock; a card on screen at 5:00 can still be rated, then Session done), one idempotency key per card reused on retry, a 404 on a rating skips the card without counting it.
**Why**: T011 acceptance criteria; code-review 0 P0/P1 (P2: reviewed_at order, fixed in 1aee88d; entry point name; lane 33 files vs C2 14), security 0 findings, independent QA PASS (ts-fsrs replay of the log matches card_states for every card), auto verify pass 2026-11-12 (commit 42909c3) and manual `/verify` PASS. ### 2026-11-12 — T015 merged: offline PWA, ordered sync, push reminders, progress export and import
**Decision**: Migration `0006_push_subscriptions`. Client: manifest + icons + `sw.js` in `src/client/public/` (caches only the static shell, never `/api` or `/auth`), IndexedDB (`idb` 8.0.4) holding the offline pack per learner and an ordered rating queue with one idempotency key per rating, `scheduleNext` reused client-side by importing `src/server/scheduler.ts` unchanged, offline banner, install offer only on Session done, `/settings` (reminders, export, import), `requireOnline()` notice for ladder generation. A 401 keeps the offline queue (clears packs and caches, goes to sign-in); explicit sign-out syncs first (2 s cap) then clears everything. A fresh `/review` load syncs queued ratings before asking for the queue and hides cards still queued.
**Why**: T015 acceptance criteria; code-review 0 P0/P1 open after the fix batch; security 0 findings; independent QA found AC 4 failing on a real Chromium (push host allowlist), a queue syncable under another account and a network drop mid-session, all fixed; the headless auto verify first failed on a stale-queue bug (a fresh load showed cards already rated offline, so a card could be reviewed twice), fixed in 8220d62 and passed. Merged 3f64cb8.
**Decided for you (auto mode, please review)**: (1) import NEVER copies the file's `cardStates` and applies log rows only when newer than the server's last review, through the same path as a sync: AC 6's literal "state replaced if newer" would break the guarantee that the log replays to the stored state; rows older than the server are skipped and counted. A learner with a card state but no log rows (only seeded data) cannot be restored from an export. (2) no lower bound on a client `reviewedAt` for a never-rated card (a restore needs old times). (3) no `clientTimeRejected` column: `usedClientTime` in the response is the record. (4) a push subscription on an endpoint another learner owns moves to the new learner (shared browser). (5) the push host allowlist: any other host is refused (the server POSTs to the endpoint a learner names). (6) migration-safety dry-run on production data is N/A (no production database).
**Known gaps (left open)**: real push delivery and a real stable Chrome endpoint host are the owner's manual check (ADR 0004); an import of 20 000 rows is one long request (about 70 s); a transient push failure skips that day's reminder; no rate limit on sync, import or subscriptions; no IndexedDB upgrade test yet (only a versioned add-only `upgrade`); ratings are ordered by `reviewedAt` only within one sync batch; offline `/ladders/<id>` and `/jobs/<id>` pages are not cached; on a shared device one account's leftover queue blocks the other account's offline pack (and hides cards with the same ids) until it is synced or cleared; T015 was labelled C2 but is 64 files and 4495 lines.
